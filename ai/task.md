# 组合测试工具（wise_combine_test）任务计划

## 1. 说明

本文档将 `design.md` 中的设计拆解为可执行任务。任务按依赖顺序排列，每个任务包含目标、交付物与验收标准。优先级分为「必须」与「可选」。

每完成一个任务，均需按 AGENTS.md 要求将本目录下应纳入版本控制的文件提交到 git 并推送到远程服务器；`.agents`、`.omo` 等 AI 本地状态目录不得提交。

## 2. 任务列表

### T1 项目骨架与构建系统（必须）

- 目标：建立可编译的 C++17 项目骨架，确定构建方式。
- 内容：创建 `src/`、`include/`、`tests/`、`examples/`、`docs/` 目录，配置不依赖第三方库的构建脚本。
- 交付物：可成功编译的最小可执行文件。
- 验收标准：干净环境执行构建成功，不引入第三方依赖。

### T2 描述语言解析器（必须）

- 目标：解析状态图与函数关系描述文件。
- 内容：实现词法/语法解析，支持 `object`、`state`、`transition`、`function`、`parameter`、`order` 等语法，并识别可选的高级关系语法 `mutex`、`constraint`。
- 交付物：解析器模块及解析结果结构。
- 验收标准：能解析合法示例；若出现 `mutex`、`constraint` 也能识别；对非法输入给出文件、行号与错误信息。

### T3 内部模型与语义校验（必须）

- 目标：将解析结果转换为状态机模型与函数关系模型，并执行语义校验。
- 内容：构建状态图邻接表、函数关系图、参数依赖图；校验状态/函数引用、类型兼容、`order` 无环、初始状态唯一、`mutex`/`constraint` 引用与语法合法性等。
- 交付物：模型模块与校验逻辑。
- 验收标准：合法描述成功建模；包括互斥/组合约束在内的各类非法描述被准确定位并拒绝。

### T4 状态迁移路径生成（必须）

- 目标：从初始状态生成到终止状态的迁移路径与调用序列。
- 内容：有界 DFS/BFS 遍历，支持最大步数、状态最大访问次数、重复路径剪枝。
- 交付物：状态迁移生成器。
- 验收标准：示例状态图生成预期路径，环路被正确截断。

### T5 函数调用序列生成（已完成）

- 目标：根据函数关系生成满足约束的组合调用序列，覆盖空流程、子集和有界重复。
- 内容：枚举函数序列，结合参数数据流、顺序、互斥、并行和组合约束过滤；`--max-function-repeats` 控制单函数重复上限。
- 交付物：函数组合生成器。
- 验收标准：示例函数关系能生成 `{push}`、`{pop}`、`{push,pop}`、`{push,push,pop}` 等有效/负向组合；参数依赖和互斥约束正确过滤。

### T6 直接执行模式（必须）

- 目标：加载用户动态库并执行生成的调用流程。
- 内容：通过 `dlopen`/`dlsym` 解析函数符号，按调用序列执行，收集返回值与状态，并按第 6.3 节问题判定标准判断通过或失败。
- 交付物：直接执行器。
- 验收标准：对示例动态库成功执行组合流程，并为每个流程输出通过或失败结论。

### T7 独立被测程序生成（必须）

- 目标：生成可独立编译运行的被测主程序，支持内存检查。
- 内容：按调用流程生成 C/C++ 代码与调用逻辑，可被 ASan 编译或 Valgrind 运行。
- 交付物：独立被测程序生成器。
- 验收标准：生成代码可编译运行，并能在 ASan / Valgrind 下检查内存问题。

### T8 日志与报告（必须）

- 目标：记录运行过程与错误，输出结构化结果。
- 内容：实现多级别日志（默认 info）、日志大小上限与轮转/清理、失败流程现场信息、文本/JSON 报告、汇总统计，并输出每个流程的通过/失败结论。
- 交付物：日志与报告模块。
- 验收标准：成功与失败流程均可复现；日志支持大小上限与轮转；报告包含通过/失败结论且格式正确。

### T9 单元测试（必须）

- 目标：覆盖 parser、model、generator、runner 各模块。
- 内容：为正常输入、非法输入与边界情况编写单元测试。
- 交付物：单元测试集。
- 验收标准：全部单元测试通过。

### T10 内存泄露与越界检查（必须）

- 目标：确认工具及被测程序无内存泄露与越界访问。
- 内容：工具以 ASan 构建并运行测试，独立被测程序在 ASan / Valgrind 下运行。
- 交付物：内存检查报告。
- 验收标准：检查无泄露与越界告警。

### T11 资源测量（必须）

- 目标：度量不同组合规模下的执行时间、内存与 CPU 占用。
- 内容：设计不同组合规模的测量场景，记录内存与 CPU 占用及执行时间随规模变化的关系。
- 交付物：测量报告。
- 验收标准：输出可复现的测量数据，能对比不同组合规模下的资源消耗变化。

### T12 用户使用说明（必须）

- 目标：提供清晰、可执行的使用说明。
- 内容：描述 DSL、命令行参数、示例、构建与内存检查方法。
- 交付物：`docs/` 下使用说明文档。
- 验收标准：新用户可按文档完成一次组合测试。

### T13 代码覆盖率 80%（可选）

- 目标：使测试覆盖率达到 80%。
- 内容：使用覆盖率工具定位未覆盖分支并补充测试。
- 交付物：覆盖率报告。
- 验收标准：整体覆盖率不低于 80%。

### T14 接口关系可扩展性增强（可选）

- 目标：支持参数传递/数据依赖、调用顺序、互斥关系和组合约束等接口关系类型。
- 内容：支持参数传递/数据依赖、调用顺序、互斥关系和组合约束等关系类型；扩展守卫表达式、多级参数传递、常量绑定，以及更丰富的调用顺序、互斥与组合约束。
- 交付物：扩展后的 DSL 与模型支持。
- 验收标准：扩展语法可解析并参与生成，覆盖 proposal 所列接口关系类型，且不引入第三方依赖。

> 说明：本任务尚未全部完成，剩余增强项已拆分为 T16–T22。

### T15 项目管理与决策记录（可选）

- 目标：记录项目管理步骤与重大决策，建立项目、代码、文档对应关系。
- 内容：维护决策记录文档，将提交与任务 ID 关联。
- 交付物：决策记录与对应关系说明。
- 验收标准：关键决策可追溯，提交与任务可对应。

### T16 参数数据流运行时绑定（可选）

- 目标：让 `parameter` 关系真正参与执行，把前序函数返回值绑定到后续函数入参。
- 内容：在执行器和独立被测程序生成器中建立参数符号表，按 `parameter` 关系解析实参来源，并在调用时传入。
- 交付物：参数绑定逻辑及可运行验证。
- 验收标准：示例中 `start(handle h)` 能收到 `init()` 返回的 `handle`，参数传递关系被正确执行。

### T17 多级参数传递与常量绑定（可选）

- 目标：支持参数依赖链和常量绑定。
- 内容：解析 `parameter <func>.<param> = <func>.<param>` 形成的依赖链，并支持把参数绑定为字面量常量。
- 交付物：扩展后的 DSL、模型数据流解析与测试。
- 验收标准：多级依赖能正确回溯；常量绑定可解析并参与生成与执行。

### T18 守卫表达式求值（可选）

- 目标：让状态迁移的 `guard` 在生成或执行阶段参与路径判定。
- 内容：为 `guard` 定义可求值的表达式语法，执行时求值并决定迁移是否可用。
- 交付物：守卫求值逻辑与测试。
- 验收标准：带 `guard` 的状态图按条件生成并执行正确路径。

### T19 更丰富的组合约束（可选）

- 目标：扩展 `constraint` 语法，支持更多组合约束表达式。
- 内容：在 `count()` 基础上支持调用次数、状态、参数值等可组合的约束表达。
- 交付物：扩展后的约束解析与求值逻辑。
- 验收标准：新增约束语法可解析并参与流程过滤，且不引入第三方依赖。

### T20 更细粒度的调用顺序/互斥约束（可选）

- 目标：支持比 `order`/`mutex` 更细粒度的关系表达。
- 内容：扩展调用顺序与互斥关系模型，例如分组互斥、条件顺序、并发或互斥组合。
- 交付物：扩展后的关系模型与生成过滤逻辑。
- 验收标准：新关系语法可解析并正确影响组合流程生成。

### T21 参数类型兼容性校验（可选）

- 目标：补齐参数关系中的类型校验。
- 内容：在 `parameter` 关系校验中比较两端类型是否兼容，而不是只校验名称存在。
- 交付物：类型兼容规则与错误定位。
- 验收标准：类型不兼容的 `parameter` 被拒绝，并给出函数、参数与原因。

### T22 生成策略接口化（可选）

- 目标：把组合生成算法抽象为可替换接口。
- 内容：定义生成策略接口，现有有界 DFS/拓扑排序实现作为默认策略，支持替换实现。
- 交付物：生成策略接口与默认实现。
- 验收标准：可替换生成策略，且现有行为保持不变。

### T23 参数数据流运行时绑定（已完成，adapter 范围）

- 目标：让 `parameter` 数据流在 adapter 执行中真实传递。
- 内容：adapter runner 维护前序函数返回值，并按 `parameter` 关系传给后续函数参数。
- 交付物：参数绑定逻辑与测试。
- 验收标准：`start.h = init.handle` 能收到 `init` 返回的 `handle`。

### T24 多级参数传递与常量绑定参与执行（可选）

- 目标：让多级依赖和常量绑定不仅被解析校验，还能参与生成或执行结果。
- 内容：对参数依赖链和常量值建立可解析的数据流，执行时用解析结果影响流程判定或报告。
- 交付物：数据流解析与执行验证。
- 验收标准：多级依赖与常量能正确解析并体现在执行结果中。

### T25 守卫表达式在状态生成与独立程序中求值（可选）

- 目标：让 `guard` 不仅影响直接执行，也影响状态路径生成和独立被测程序。
- 内容：在状态路径生成中应用守卫约束；在独立程序中生成守卫判断代码。
- 交付物：状态生成守卫剪枝与独立程序守卫代码。
- 验收标准：带守卫的状态图按条件生成路径，独立程序执行守卫判断。

### T26 状态与参数值组合约束（可选）

- 目标：在 `count()` 约束之外支持状态、参数值等组合约束。
- 内容：扩展 `constraint` 语法与求值器，支持引用状态和参数值。
- 交付物：扩展约束解析与求值逻辑。
- 验收标准：新增约束可解析并参与流程过滤。

### T27 条件顺序与并发/互斥组合（可选）

- 目标：支持比 `order`/`mutex` 更细粒度的调用顺序与互斥组合。
- 内容：扩展关系模型，支持条件顺序、并发约束、互斥组合等。
- 交付物：扩展关系解析与生成过滤。
- 验收标准：新关系语法可解析并正确影响组合流程生成。

### T28 预期输出/预期结果判定（部分完成，按模式分层）

- 目标：支持用户声明预期返回结果和预期标准输出，并按预期判定通过或失败。
- 内容：`expect` 在 direct、adapter、standalone 中比较返回值；`expect_output` 在 adapter 中比较标准输出，direct/standalone 遇到不支持组合时明确拒绝。
- 交付物：预期结果解析、执行比较与报告。
- 验收标准：预期返回值不一致被判定为失败；`expect_output` 在 adapter 中正确判定，在 direct/standalone 中不静默跳过。

### T29 独立被测程序能力对齐（已完成，限定范围）

- 目标：让独立被测程序与直接执行模式具备一致的守卫和预期结果判断能力。
- 内容：在独立程序生成器中加入守卫求值和预期结果检查；参数绑定明确不属于 direct/standalone 范围。
- 交付物：生成代码能力对齐及测试。
- 验收标准：零参函数在独立程序与 direct 模式得到一致的守卫和返回值判断；带参流程被显式拒绝。

### T30 类型化标量协议（可选，部分完成）

- 目标：让 adapter JSON 协议具备可验证版本和严格解析。
- 内容：协议版本固定为 1；实现严格 JSON 解析，接受合法空白/字段顺序/转义，拒绝尾随内容、未知版本和缺失字段；请求增加 `return_type` 和 `arg_types`。强类型标量仍作为后续扩展。
- 交付物：类型化标量协议与单元测试。
- 验收标准：合法 JSON 变体可解析，协议负例被拒绝。

### T31 direct 模式精确预期输出（可选，限定为 adapter）

- 目标：保证 `expect_output` 在支持该能力的执行模式中可验证。
- 内容：`expect_output` 由 adapter 模式提供；direct/standalone 不支持时显式拒绝，避免静默跳过。
- 交付物：direct 输出捕获逻辑与测试。
- 验收标准：adapter 模式能对 `expect_output` 正确判断；direct/standalone 对不支持组合给出明确错误。

### T32 统一 mutant oracle 回归（发布前）

- 目标：把 Q1–Q6 有状态队列 oracle 接入仓库回归。
- 内容：新增 `test/oracle/` 下的统一 SUT、模型、adapter 和运行脚本，`make check` 自动执行 clean/mutant 各两次。
- 验收标准：clean 12/12 返回 0 且全部 passed；mutant 12/12 返回非零且全部 failed。

### T33 trace/replay 元数据（发布前）

- 目标：保存可复现、可重放的流程执行证据。
- 内容：`--trace` 输出包含模型摘要、seed、输入文件、flow ID、expected/actual 和 flow 数组的 JSON；`--replay` 读取并恢复 flows。
- 验收标准：同一 trace 文件可重新执行，且报告元数据一致。

### T34 覆盖率口径（发布前）

- 目标：明确父子进程覆盖率归集边界。
- 内容：提供 `make coverage` 命令，并在报告中说明当前统计口径和子进程覆盖限制。
- 验收标准：可重复生成覆盖率数字；不把父进程数字声明为完整 fork/exec 覆盖证明。

## 4. 执行顺序

1. 按依赖顺序先完成 T1 至 T8 的核心功能。
2. 完成 T9 单元测试。
3. 完成 T10 内存检查与 T11 资源测量。
4. 完成 T12 使用说明。
5. 按需完成 T13、T14、T15 可选任务。
6. 按需完成 T16 至 T22 可选增强任务。
7. 按需完成 T23 至 T29 增强任务。
8. T30 当前已完成协议版本与严格 JSON 解析，T31 当前限定为 adapter；后续按需扩展，不再标为“待以后完成的核心任务”。
9. 发布前完成 T32、T33、T34。

## 5. 提交规范

每个任务完成后执行：

1. 运行相关测试，确认通过。
2. 将本目录下应纳入版本控制的文件加入 git；不要加入 `.agents`、`.omo` 等 AI 本地状态目录及编译、测试产物。
3. 提交，提交信息包含任务 ID 与简要说明。
4. 推送到远程 `origin/plan_goal`。

编译和测试产生的二进制文件、构建目录按 `.gitignore` 排除，不提交。
