# 组合测试工具（wise_combine_test）设计文档

## 1. 概述

本文档描述组合测试工具的技术设计，作为 `task.md` 任务拆解的依据。工具通过解析用户描述的状态图与函数关系，生成组合调用流程并执行，检测程序问题。

实现语言采用 C++17，仅使用 C++ 标准库与 POSIX 接口，不引入第三方库。

每个组合调用流程执行后，按第 6.3 节的标准判定为通过或失败，基本判定依据为：不崩溃、无内存错误、无断言失败，且与用户提供的预期输出或预期结果一致（若提供了预期）。

## 2. 总体架构

工具由以下模块组成，按数据流向串联：

```
描述文件
  -> 词法/语法解析器 (parser)
  -> 内部模型 (model)
  -> 组合生成器 (generator)
  -> 执行器 (runner)
  -> 报告与日志 (reporter/logger)
```

各模块职责：

- **parser**：读取用户描述文件，构建抽象语法结构。
- **model**：将抽象语法转换为状态机模型与函数关系图模型，并完成语义校验。
- **generator**：基于模型生成组合调用流程。
- **runner**：加载用户被测函数并执行调用流程，收集结果。
- **reporter/logger**：输出结构化结果与运行日志。

模块之间通过内部模型接口解耦，便于独立测试与替换实现。

## 3. 描述语言（DSL）

描述语言采用自定义文本格式，按段落组织，避免引入第三方解析库。格式分为「状态图描述」和「函数关系描述」两类，可位于同一文件或不同文件。

### 3.1 状态图描述

状态图描述对象、状态、初始状态、终止状态以及状态迁移。

```
object <对象名> {
  state <状态名> [initial] [final]
  transition <源状态> -> <目标状态> by <函数名> [guard <条件表达式>]
}
```

字段说明：

- `state`：声明一个状态；`initial` 表示初始状态，`final` 表示终止状态。
- `transition`：声明一条状态迁移，`by` 后为触发迁移的函数，`guard` 为可选守卫条件。

示例：

```
object connection {
  state IDLE initial
  state READY
  state BUSY
  state DONE final
  state ERROR final

  transition IDLE -> READY by init()
  transition READY -> BUSY by start()
  transition BUSY -> DONE by finish() guard return==0
  transition BUSY -> ERROR by fail() guard return!=0
}
```

### 3.2 函数关系描述

函数关系描述一组函数、参数、参数之间的传递关系、调用顺序约束，以及可选的互斥关系与组合约束。

```
function <函数名>(<参数列表>) [-> <返回参数>]
parameter <函数名>.<参数名> = <函数名>.<参数名>
order <前驱函数> before <后继函数>
```

字段说明：

- `function`：声明被测函数及其参数、返回参数。
- `parameter`：声明参数之间的数据传递关系，右值为参数来源。
- `order`：声明调用顺序约束，前驱函数必须先于后继函数调用。
- `mutex`：声明两个函数互斥，不能出现在同一组合调用流程中（可选高级要求）。
- `constraint`：声明附加组合约束，表达式可引用函数调用次数、状态或参数值（可选高级要求）。

示例：

```
function init() -> handle
function start(handle h, config c)
function finish(handle h) -> status
function fail(handle h) -> status
function release(handle h)

parameter start.h = init.handle
parameter finish.h = init.handle
parameter fail.h = init.handle
parameter release.h = init.handle

order init before start
order init before finish
order finish before release

mutex start finish
```

`mutex` 与 `constraint` 属于第 3.2 节高级关系，本期为可选实现；若描述中出现，解析器应能识别并写入模型，执行阶段按第 5.2 节与第 6.3 节处理。

### 3.3 约束与校验

解析器在构建模型时执行以下校验：

- 迁移引用的源/目标状态已声明。
- 迁移引用的函数已在函数关系中声明。
- 参数传递的两端参数类型兼容。
- `order` 不形成循环依赖。
- `mutex` 引用的函数已声明，且互斥关系不与调用顺序形成无法满足的冲突。
- `constraint` 表达式语法合法，且引用的函数、状态或参数已声明。
- 存在且仅存在一个初始状态。

校验失败时给出包含文件位置和原因的明确错误信息。

## 4. 内部模型

### 4.1 状态机模型

状态机模型由以下要素构成：

- 状态集合，每个状态带 `initial`、`final` 标记。
- 迁移集合，每个迁移包含源状态、目标状态、触发函数和可选守卫。

迁移建模为有向边，状态建模为有向图顶点。

### 4.2 函数关系模型

函数关系模型由以下要素构成：

- 函数集合，每个函数包含参数列表与返回参数。
- 参数传递关系，表示参数值的来源。
- 调用顺序约束，建模为偏序关系。
- 互斥关系，表示不能同时出现在同一组合流程中的函数集合（可选）。
- 附加组合约束，保存为可求值表达式（可选）。

函数与状态迁移通过迁移上的触发函数关联。

### 4.3 数据结构

内部模型使用标准库容器实现：

- 状态机与函数关系图：`std::unordered_map` 建立名称到对象的索引，邻接表存储边关系。
- 组合生成过程的中间路径：`std::vector` 存储调用序列，`std::deque` 或显式栈进行遍历。
- 参数符号表：记录参数来源与类型。

所有资源由 RAII 管理，避免手动内存管理。

## 5. 组合生成算法

### 5.1 状态迁移路径生成

从初始状态出发，对有向状态图做深度优先或广度优先遍历，枚举从初始状态到终止状态的迁移路径。为避免环路导致无限遍历，采用以下策略：

- 对每个状态设置最大访问次数。
- 限制单条路径的最大迁移步数。
- 检测重复状态序列，剪枝已访问过相同状态序列的分支。

每条迁移路径转换为一个调用序列，迁移上的守卫条件在生成时记录，执行时求值。

### 5.2 函数调用序列生成

在函数关系图上，依据调用顺序偏序约束生成拓扑序。参数传递关系用于确定每个函数实参的来源，从而生成可执行的调用序列。

当存在多个满足约束的拓扑序时，枚举所有有效顺序；对顺序无约束的函数组，按可配置策略生成排列组合。

若存在互斥关系，则排除同时包含互斥函数的调用序列；附加组合约束在生成时记录，并在执行前或执行后求值，不满足约束的流程被标记为无效或失败。

### 5.3 参数数据流解析

从返回参数开始，沿 `parameter` 声明回溯参数来源，建立参数依赖图。执行调用序列时，前一函数产生的返回值作为后一函数的实参传入。

若参数来源无法解析或存在循环依赖，生成阶段报错并停止。

### 5.4 边界与剪枝

为控制组合爆炸，生成器提供可配置上限：

- 最大路径步数。
- 单次运行最大调用流程数量。
- 状态最大重复访问次数。
- 函数排列组合的最大规模。

达到上限时输出告警，提示结果被截断。

## 6. 执行器

执行器支持两种模式，均加载用户提供的被测函数。

### 6.1 直接执行模式

通过 `dlopen` 加载用户编译的动态库，按符号名解析被测函数，并依据生成序列直接调用。该模式只支持无参 C ABI 函数；如果流程包含带参函数，执行前明确失败并提示使用 adapter。

### 6.2 独立被测程序模式

生成一个独立的 C/C++ 主程序，包含所有调用流程的调用代码，用户编译后可独立运行。该模式用于在 ASan 或 Valgrind 下运行，完成内存泄露与越界检查。

生成的被测程序固定为零参 C ABI 调用约定，并提供简单的状态与返回值检查逻辑。带参流程不生成独立程序，应使用 adapter 模式。

生成的源文件默认输出到 `build/wise_standalone.cpp`。

### 6.3 问题判定标准

每个组合调用流程执行后，按以下信号判定为通过或失败：

- 被测程序崩溃或异常终止；
- 断言失败；
- 内存错误（ASan / Valgrind 检测到内存泄露、内存越界访问、重复释放等）；
- 实际输出或返回结果与用户提供的预期输出或预期结果不一致。

若用户未提供预期输出或预期结果，则以「不崩溃、无内存错误、无断言失败」作为最低通过标准。判定结果随结果报告输出。

## 7. 内存检查

内存检查通过以下方式实现：

- 工具自身以 `-fsanitize=address` 编译构建，并在 CI 或本地测试中运行，检查工具自身的内存问题。
- 生成的独立被测程序支持 ASan 编译与 Valgrind 运行，检查被测函数的内存泄露与越界访问。
- 测试报告记录每次内存检查的结论。

## 8. 日志与报告

### 8.1 运行日志

日志记录到标准错误或指定文件，包含时间戳、日志级别、模块、调用流程标识与详细信息。日志级别可配置为 error、warning、info、debug，默认级别为 info。

日志默认输出到当前工作目录下的 `build/wise_combine_test.log`，可通过 `--log-file` 指定其他位置。为支持日志大小上限、轮转与清理：

- 单个日志文件达到 `--log-max-size`（默认 10 MiB）后进行轮转；
- 保留最近 `--log-rotate-count`（默认 5）个日志文件，超出部分删除或覆盖。

错误日志至少包含：失败调用流程、当前函数、参数、返回值与失败原因，便于复现与定位。

### 8.2 结果报告

执行结束后输出结构化结果，包含：

- 生成的调用流程总数。
- 每个调用流程的状态（成功、失败、崩溃、超时）。
- 失败流程的调用栈信息。
- 汇总统计。

报告可输出为文本或 JSON 格式。

## 9. 命令行接口

工具提供命令行入口，核心用法如下：

```
wise_combine_test <描述文件> [选项]
```

主要选项：

- `--mode direct|standalone`：选择执行模式。
- `--max-depth <n>`：限制最大路径步数。
- `--max-flows <n>`：限制最大调用流程数量。
- `--log-file <path>`：指定日志输出文件。
- `--log-max-size <bytes>`：设置单个日志文件大小上限。
- `--log-rotate-count <n>`：设置保留的历史日志文件数量。
- `--report <text|json>`：指定报告格式。

未指定参数时使用默认值：`--mode direct`、`--max-depth 32`、`--max-flows 1000`、`--log-file build/wise_combine_test.log`、`--log-max-size 10485760`（10 MiB）、`--log-rotate-count 5`、`--report text`。

## 10. 测试与测量

### 10.1 单元测试

对 parser、model、generator、runner 各模块编写单元测试，覆盖正常输入、非法输入与边界情况。

### 10.2 覆盖率

使用编译器覆盖率工具统计代码覆盖率，以 80% 为可选目标。

### 10.3 内存检查

对工具及生成的被测程序执行 ASan / Valgrind 检查，确认无内存泄露与越界访问。

### 10.4 资源测量

记录不同组合规模下被测程序的内存占用与 CPU 占用，并对比分析其随规模变化的关系，同时测量执行时间，形成测量报告。

## 12. 错误处理

- 描述文件语法错误：报告文件、行号与错误信息。
- 语义校验错误：报告具体违反的约束。
- 动态库加载失败：报告库路径与 `dlerror` 信息。
- 符号解析失败：报告缺失的符号名。
- 执行崩溃或超时：在报告中标记，并输出该流程标识以及截至失败时已产生的日志。

## 13. 可扩展性设计（可选高级要求）

为支持参数传递/数据依赖、调用顺序、互斥关系和组合约束等接口关系类型，模型预留以下扩展点：

- 迁移守卫与函数返回值可扩展为更丰富的条件表达式。
- 参数关系支持多级传递和常量绑定。
- 调用顺序支持更细粒度的并发或互斥约束。
- 生成策略以接口形式定义，便于替换为其他组合算法。

这些扩展作为可选目标，在不引入第三方依赖的前提下逐步实现。

## 14. 关键决策记录

- 采用 C++17 与标准库实现，满足「不引入第三方库」与内存检查要求。
- 采用自定义文本 DSL，避免第三方解析库。
- 执行器采用「直接执行 + 独立被测程序」双模式。
- 状态图与函数关系统一映射为有向图，统一采用图遍历与拓扑排序生成组合。
