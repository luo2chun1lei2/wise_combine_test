# 基于模型的测试（Model-Based Testing, MBT）

## 1. 概述

基于模型的测试是一种软件测试方法：先为被测系统建立一个抽象行为模型，再根据模型和覆盖准则自动生成测试用例，执行后把实际行为与模型预期进行比较。

与“手动逐条编写用例”不同，MBT 的核心思路是把期望行为集中描述一次（模型），然后让工具系统性地派生大量、可度量的测试用例。

## 2. 核心组成

- **模型**：对被测系统行为的抽象描述，常见形式有状态机、函数/操作契约、数据流等。
- **生成算法**：从模型按覆盖准则生成测试用例，即调用序列或状态路径。
- **覆盖准则**：衡量用例集合充分性的标准，例如状态覆盖、转换覆盖、转换对覆盖、N-switch 覆盖、路径覆盖等。
- **执行器**：把生成的用例真正运行在被测系统上。
- **预言（oracle）**：判断一次运行是否正确的预期状态或输出。

## 3. 与本项目两个测试目标的匹配

### 3.1 目标一：函数调用序列测试

把一组函数看成一个“带资源状态的操作系统”。每个资源（如文件句柄）是有生命周期的对象，函数调用是带前置条件、后置效果的状态转换。

以文件句柄为例，其类型状态（typestate）可以写成：

- `CLOSED` 经过 `open` 变为 `OPEN`
- `OPEN` 经过 `write` 仍为 `OPEN`
- `OPEN` 经过 `close` 变为 `CLOSED`

MBT 从这个模型生成合法调用序列：从初始状态出发，每一步只选择前置条件满足的函数，并跟踪 `open` 产生的句柄如何传递给 `write` 和 `close`。这样生成的序列具有真实语义关系，能够发现调用顺序错误、句柄在关闭后继续使用、资源泄漏等问题。这与类型状态、资源生命周期、API 误用检测的思路一致。

### 3.2 目标二：状态机路径测试

把 UML 状态图直接当作有限状态机（FSM）：状态是节点，事件驱动的转换是边。MBT 按覆盖准则生成不同长度、不同途径的路径，例如：

- 状态覆盖：每个状态至少到达一次。
- 转换覆盖：每条转换至少执行一次。
- 转换对覆盖：所有连续两条转换都被覆盖。
- N-switch 覆盖：所有连续 N 条转换都被覆盖。
- 路径覆盖：给定长度上限内覆盖所有路径。

随后执行这些路径，把运行后的状态与模型期望状态比较，检查状态切换是否正确。这是经典的基于 FSM 的测试，方法上对应转换游、W-method、中国邮路等。

## 4. 为什么它正好匹配

两个目标的共同点是：用户先描述一个行为模型（函数语义或状态图），再要求工具自动生成并执行“有意义的组合”。这正是 MBT 的定义。这里的“组合”是调用序列或状态路径的组合，而不是经典组合测试里的参数取值组合（t-way 覆盖数组）。

## 6. 好处与局限

好处：

- 行为描述集中、可复用，修改一处模型即可重新生成全部用例。
- 覆盖可度量，能定量说明测试的充分程度。
- 比手工写用例更系统，减少遗漏。
- 适合状态明确、交互关系复杂的接口和协议。

局限与前提：

- 模型本身必须正确，否则错误会系统性地传导到用例。
- 需要定义 oracle，否则只能发现崩溃，难以判断逻辑错误。
- 状态和序列数量可能爆炸，需要覆盖准则、长度上限和剪枝控制。
